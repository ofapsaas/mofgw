# ADR-011: Sync automático del catálogo upstream — binario separado `mofgw-sync` con fetch+cache+lock+digest

- **Status**: Accepted (feature 019-001-fetch-modelsdev, primera del epic 019-provider-sync-automation)
- **Date**: 2026-09-11
- **Deciders**: Ofap (dueño del proceso delegado por Pablo — HITL, goal mode, 11 Sep 2026)
- **Confianza**: Alta (decisión fundacional del epic: codificada en el plan §"Decisión de arquitectura clave" + spec D1-D10/I1-I10, implementada en `internal/modelsdev`, verificada empíricamente por la suite completa 763/30 `-race` y por la review — bloqueantes resueltos por decisión HITL delegada)

## Contexto

mofgw mantiene `config.yaml` (providers[].models, pricing, model_metadata) a mano. El catálogo
upstream (models.dev + listas autorizadas Zen/Go) cambia sin aviso y el skill `mofgw-provider-sync`
documenta un workflow manual con error humano. opencode resuelve lo mismo con fetch+cache+lock+TTL+digest;
el epic 019 replica ese mecanismo nativamente en mofgw. El servidor mofgw debe permanecer simple y desacoplado
del sincronizador: corriendo desde cron/timer y por CLI, no desde un endpoint admin in-server.

## Opciones consideradas

### Opción A: Endpoint admin in-server (DESCARTADA)
Pros: sin binario nuevo. Contras: acopla el sync al runtime del proxy (el timer podía tumbar al servidor),
contraria al criterio de cierre de la epic (sync desacoplado, corre desde cron/timer/CLI), superficie de ataque admin
sobre el servidor. Descartada en el plan del epic.

### Opción B: Subcomando `mofgw sync` (DESCARTADA)
Pros: un solo binario. Contras: mezcla los flags del servidor (`-config/-verbose/-log-file`) con los del sync,
acopla el timer (019-006) al proceso del proxy y carga el runtime del servidor aunque solo se quiera sincronizar.
Descartada en el spec 019-001 (alternativas desestimadas).

### Opción C: Binario separado `cmd/mofgw-sync` + paquete `internal/modelsdev` — ELEGIDA
El sync es un binario aparte que consume el paquete `internal/modelsdev` (fetch+cache+lock+digest reutilizable).
El servidor mofgw no importa nada del sync (I1, cero impacto). El paquete es el contrato tipado que consumen
019-002/003/007.

## Decisión

- **Binario separado `cmd/mofgw-sync`** (wiring en 019-004), **paquete `internal/modelsdev`** entregado en 019-001.
- **Cache persistente en disco** en `os.UserCacheDir()/mofgw/models-dev.json` (env `MOFGW_CACHE_DIR` override del
  path base; fallback `os.TempDir()/mofgw`), TTL default 5m por **mtime**, escritura siempre **temp+rename atómica**
  (patrón `internal/metrics/persist.go`), sidecar primero / cache último = punto de commit.
- **Lock cross-process** con `syscall.Flock` `LOCK_EX|LOCK_NB` sobre un **lock file dedicado `<path>.lock`**
  (NUNCA el propio cache: el rename atómico invalidaría locks sobre él — I10; el lock file dedicado evita también
  bloquear a los lectores `Get()`). Lock-first antes del TTL-check. Busy → `ErrLockBusy` rápido, sin espera.
- **Digest sha256 en sidecar `<path>.sha256`**: skip de writes byte-idénticos (no reescribir cache ni sidecar,
  `changed=false`, log `skipped_identical`). Lección opencode PR #44282.
- **Retry/semántica de errores (D9 reinterpretado por la review B1):** 2 intentos totales, backoff ~500ms,
  SOLO transporte `network`/5xx son retryable; **`timeout` NUNCA reintenta** (un intento colgado ya consumió su
  presupuesto → duplicaría latencia); 4xx tampoco. `classifyTransport` distingue `DeadlineExceeded` (timeout real)
  de `Canceled` (cancelación del llamador). Errores tipados `errors.Is`: `ErrFetchDisabled`/`ErrLockBusy`/
  `FetchError{Type: timeout|network|canceled|status|parse}`.
- **Knob `MOFGW_DISABLE_MODELS_FETCH=1`**: `Fetch` devuelve `ErrFetchDisabled` sin emitir request; `Refresh`
  sirve cache si existe (`(false,nil)`), si no → `ErrFetchDisabled` (estado esperado, no fallo de red).
- **Fail-soft en runtime** (cache stale servido + warn) / **fail-loud** sin cache. Precedente: state corrupto no
  bloquea el arranque (main.go:183-189).

## Razones

1. **Desacople servidor/sync**: el binario separado y el paquete sin imports hacia config/proxy/router/cmd
   garantizan I1 (cero impacto en el servidor, verificado manualmente — sin import-linter en el repo).
2. **El upstream manda (I2)**: el paquete solo parsea y persiste; no filtra IDs, no mapea, no deriva ni normaliza
   (eso es 019-003). Parseo tolerante (schema variable con `tiers`/`context_over_200k`/`input_audio` solo en
   algunos modelos; 0 ocurrencias de `variants`/`supported_parameters`) → cambios aditivos upstream no rompen (I9).
3. **Lock+digest = corredores concurrentes seguros**: el 2º proceso que corre el sync falla rápido
   (`ErrLockBusy`) sin corromper; el digest evita rewrites byte-idénticos y conserva el cache byte-fiel al upstream.
4. **Semántica de timeout correcta (corrección de la review)**: el spec original (P4 vs D9) era internamente
   contradictorio; la revisión independiente evitó perpetuar 2 intentos de 10s en producción. La reinterpretación
   queda lockeada: solo transporte es transitorio.
5. **Stdlib-only**: no hay librería de flock (grep 0 matches); `syscall.Flock` cubre el caso Linux-only del repo
   (sin build tags Windows en el árbol). El único path externo del cache pasa por stdlib `os.UserCacheDir`.

## Consecuencias

- **Positivas**: paquete reutilizable como contrato tipado para 019-002/003/007; sync desacoplado del servidor
  (timer/CLI seguro); cache persistente reutilizado entre corridas; no-regresión asegurada por construcción (I1) y
  verificada por suite 763/30 `-race`.
- **Negativas**: binario adicional a construir/versionar (019-004); atomicidad cross-file real del par
  cache+sidecar NO es perfecta (fallo tras sidecar OK → self-heal en próximo refresh, `Get()` sirve cache viejo
  interim — aceptado en B2); el test del override `MOFGW_CACHE_DIR` quedó sin escribir (fragilidad de mockear HOME
  roto — deuda).
- **Seguridad**: request GET anónimo con solo UA (sin auth/secretos, I7); cache en UserCacheDir (dir 0o750).
- **Deuda transferida al epic**: derivación de `supported_parameters`/`variants` → 019-003; hot-reload (017
  pausada) → 019-005 default = restart systemd.
