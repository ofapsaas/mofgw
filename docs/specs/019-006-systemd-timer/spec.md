Resuelve el repo root caminando hacia arriba desde el CWD del test (que `go test` fija al dir del paquete) hasta el dir que contiene `go.mod`, y lee `scripts/systemd/mofgw-sync.{service,timer}` vía `os.ReadFile`.   4. **Harness bash extendido**: `scripts/test-install.sh` (MODIFICADO) agrega tests de contrato para los artefactos nuevos, siguiendo el patrón existente: sandbox `MOFGW_HOME=$(mktemp -d)` + `MOFGW_SKIP_SYSTEMCTL=1` (test-install.sh:7-9,40-44), guard RED si el script no existe (test-install.sh:31-37).
- **D2 — Semántica del timer (LOCKEADA, decisión HITL 1).** Monotónico, NO de calendario: `[Timer] OnBootSec=10min` + `OnUnitActiveSec=60min`. Sin `OnCalendar`, sin `Persistent=` (es no-op sin OnCalendar y evita semántica de catch-up confusa), sin `RandomizedDelaySec`. El intervalo es 60 min fijo del epic (plan.md:39) — jamás knob. `Unit=` implícito: systemd deriva `mofgw-sync.timer` → `mofgw-sync.service` por emparejamiento de nombre (derivación estándar; el golden test valida el emparejamiento por nombre de archivo). Comportamiento esperado documentado: al `enable --now` un timer cuyo `OnBootSec` ya venció (boot > 10 min atrás), systemd dispara la primera corrida inmediatamente — esto es DESEADO (deja logs del sync visibles al instalar, criterio plan.md:62; aceptado por HITL). El solapamiento de runs está estructuralmente excluido: el service es `Type=oneshot` (D3) — si el timer dispara mientras un run está activo, systemd lo colapsa, no lo solapa.
- **D3 — Service unit del sync (LOCKEADA, decisión HITL 4).** `Type=oneshot`, `ExecStart=%h/.local/bin/mofgw-sync`, `EnvironmentFile=-%h/.config/mofgw/env`, `StandardOutput=journal`, `StandardError=journal`. SIN `Restart=` (I1 — el timer es el único scheduler; tras un exit ≠ 0 el oneshot queda `failed` visible en `systemctl status` y el timer lo re-dispara en el próximo vencimiento, que ES el mecanismo de retry). SIN sección `[Install]` (jamás se enablea manual: solo el timer lo activa). SIN `TimeoutStartSec`: para `Type=oneshot` sin `RemainAfterExit` el timeout de arranque es infinito por defecto (systemd.service(5)) — necesario porque el peor caso del ciclo (fetch de 4 fuentes con retry + restart 30s + ventanas de verificación 30s+30s + rollback, P11 de 005) excede el default de 90s. Sin `RemainAfterExit` (el estado "inactive" tras cada run es la normalidad que el timer re-dispara).
- **D4 — EnvironmentFile compartido y tolerante (LOCKEADA, decisión HITL 4).** El sync hereda el MISMO env file del server: `EnvironmentFile=-%h/.config/mofgw/env` (el unit real del server usa el mismo file sin prefix "-", verificado en `~/.config/systemd/user/mofgw.service:7`). El prefix `-` es DELIBERADO: el sync NO consume las provider keys (`MOFGW_GO_*`/`QWEN`/`OPENROUTER` son del server; los fetch de 001/002 son catálogos públicos) — la única var que le importa es `MOFGW_SYNC_VERIFY_KEY` (leída en runtime, cmd/mofgw-sync/main.go:172-176), y su ausencia ya tiene semántica fail-soft lockeada (D7 de 005: F1+F2 + warning `verify_key`, reloadsig.go:154). Con file ausente el sync corre igual; con `-` systemd no falla el unit. El file JAMÁS es creado ni modificado por install.sh (I4); agregar `MOFGW_SYNC_VERIFY_KEY` es acción del operador, documentada (P10).
- **D5 — Instalación del binario mofgw-sync (LOCKEADA, decisión HITL 5).** Función `install_sync_binary` en install.sh, espejo exacto de `install_binary` (install.sh:85-100) para el bin sync. Resolución (idéntica precedencia, nombre propio): `$MOFGW_SYNC_BIN_SRC` si está set (die si inexistente) → `$REPO_ROOT/mofgw-sync` prebuilt si existe → `go build -o "$MOFGW_BIN_DIR/mofgw-sync" ./cmd/mofgw-sync` (construye directo al destino, sin artefacto en el repo — patrón install.sh:96). `chmod 755` (install.sh:99). Var nueva documentada en el header del script junto a `MOFGW_BIN_SRC` (install.sh:28).
- **D6 — Corrección del trap: backup-on-overwrite para TODAS las unidades (LOCKEADA, decisión HITL 3).** El patrón actual `cmp → mv` de install.sh:138-144 pisa sin rescate cualquier unit divergido: verificado en host que `~/.config/systemd/user/mofgw.service` divergió del template (env-file línea 7 + flags línea 8 ausentes en install.sh:121-137) → re-correr install.sh HOY destruiría la config del operador. Contrato nuevo: si el unit destino existe y difiere del contenido a instalar, se mueve a `<unit>.bak.<timestamp>` ANTES de instalar (patrón config.bak de install.sh:204); si es idéntico, no-op sin backup; si no existe, instalación directa sin backup. Aplica a los tres units que instala install.sh: `mofgw.service` (existente), `mofgw-sync.service` y `mofgw-sync.timer` (nuevos). Los `.bak.*` se acumulan (timestamp único) y JAMÁS se borran (ni por re-instalación ni por uninstall — espejo del tratamiento de config.bak, install.sh:152-156/204).
- **D7 — Activación y verificación del timer (LOCKEADA, decisión HITL 5).** Paso `start_sync_timer` de install.sh, corriendo DESPUÉS de `start_service` (el server debe estar activo y healthy antes de agendar syncs — si el server falla verificación, install muere antes de crear el timer, patrón die de install.sh:158/170/178). Pasos, todos vía el wrapper `systemctl_user` que respeta `MOFGW_SKIP_SYSTEMCTL` (install.sh:61-67): (1) `daemon-reload`; (2) `enable --now mofgw-sync.timer`; (3) verificación: `systemctl --user list-timers mofgw-sync.timer --no-legend` muestra el timer activo (o falla `is-enabled` ≠ enabled) → die con mensaje claro si no. No se espera la primera corrida (disparo puede ser inmediato por D2): la verificación es de AGENDA (timer cargado y activo), no de ejecución.
- **D8 — `--once` no cambia (LOCKEADA, decisión HITL 4 del discovery).** El flag `--once` es no-op declarado por contrato de 004 (cmd/mofgw-sync/main.go:104-107, D1.3: "el scheduling es 006") — era residuo del plan pre-004. 006 NO lo promociona a modo real, NO toca `main.go`, NO agrega flags ni knobs de intervalo (superficie mínima, precedente D4 de 005: el nombre del unit es constante, no knob).

## Contrato (postcondiciones)

- **P1 — Contenido exacto de `scripts/systemd/mofgw-sync.service`.** Archivo commiteado con EXACTAMENTE esta forma (sin `[Install]`, sin `Restart`, sin `TimeoutStartSec`): `[Unit]` con `Description=mofgw-sync - sincronización del catálogo de providers de mofgw (epic 019)`; `[Service]` con `Type=oneshot`, `ExecStart=%h/.local/bin/mofgw-sync`, `EnvironmentFile=-%h/.config/mofgw/env`, `StandardOutput=journal`, `StandardError=journal`. Nada más.
- **P2 — Contenido exacto de `scripts/systemd/mofgw-sync.timer`.** Archivo commiteado con EXACTAMENTE: `[Unit]` con `Description=mofgw-sync timer - sincronización del catálogo cada 60 minutos`; `[Timer]` con `OnBootSec=10min` y `OnUnitActiveSec=60min` (y NADA más: cero `OnCalendar`, cero `Persistent`, cero `AccuracySec`, cero `Unit=`); `[Install]` con `WantedBy=timers.target`.
- **P3 — Instalación idempotente de las unidades del sync.** `install_sync_units` copia ambos archivos de `scripts/systemd/` a `$MOFGW_UNIT_DIR` (default `$MOFGW_HOME/.config/systemd/user`, install.sh:45) con `mkdir -p`: contenido idéntico al existente → no-op con log (patrón install.sh:138-140); ausente → instala; difiere → backup `.bak.<ts>` + instala (P4). Re-corridas no duplican ni acumulan backups cuando el contenido no cambia.
- **P4 — Backup-on-overwrite universal.** La mecánica de P3 aplica también a `mofgw.service`: re-correr install.sh en un host con el unit real divergido (verificado: env-file + flags del operador) produce `mofgw.service.bak.<ts>` con el contenido previo INTACTO y el unit nuevo instalado. El contenido previo es byte-exacto (rename/mv, jamás regeneración).
- **P5 — Instalación del binario sync.** Tras install.sh exit 0 existe `$MOFGW_BIN_DIR/mofgw-sync` (755), resuelto por la precedencia de D5. El binario server `$BIN` y su resolución (install.sh:85-100) quedan byte-intactos en su comportamiento (solo comparten el patrón).
- **P6 — Orden de instalación.** El main de install.sh ejecuta: `install_binary` → `install_config` → `install_unit` → `install_sync_binary` → `install_sync_units` → `start_service` → `start_sync_timer`. Si `start_service` muere (server no sano, install.sh:170-184), `start_sync_timer` NO corre (el timer no se agenda sobre un install fallido).
- **P7 — Activación con guardia dry-run.** Con `MOFGW_SKIP_SYSTEMCTL=1`: los pasos de D7 se loguean como dry-run y jamás tocan systemd (wrapper install.sh:61-67 — el harness debe pasar sin systemd real). Sin la guardia: `daemon-reload` + `enable --now` + verificación de agenda (D7 paso 3), die claro si la verificación falla.
- **P8 — Sin secrets generados (hereda P13 de 005).** install.sh jamás crea, edita, ni inventa `~/.config/mofgw/env` ni ninguna key (`MOFGW_SYNC_VERIFY_KEY` incluida): solo REFERENCIA el file en el unit (P1). Si el file no existe, la instalación no falla por ello (prefix `-`, D4) y la degradación D7 de 005 gobierna el runtime.
- **P9 — Trazabilidad del `--once`.** El flag queda no-op (main.go:104-107); su doc en el header del binario y en el spec de 004 no cambia. Cero diffs en `cmd/mofgw-sync/main.go`.
- **P10 — Documentación del requerimiento de paridad.** El unit del sync referencia el env compartido; la doc del deploy (README o sección del header de install.sh) registra: para paridad automatizada F3, el operador agrega `MOFGW_SYNC_VERIFY_KEY=<key de cliente>` a `~/.config/mofgw/env` (key ya registrada en clients.yaml — D7 de 005). Sin ella, cada corrida del timer corre F1+F2 con warning (P9 de 005).
- **P11 — Uninstall del sync.** `--uninstall` extiende el existente (install.sh:191-208): `systemctl --user disable --now mofgw-sync.timer` (|| true, tolerante a ausencia), borra `$MOFGW_UNIT_DIR/mofgw-sync.{service,timer}` y `$MOFGW_BIN_DIR/mofgw-sync`; NO borra `.bak.*` de units ni de config; el unit/binario/config del server conserva el comportamiento vigente (install.sh:194-206) MÁS el backup-on-overwrite de P4 en re-instalaciones.
- **P12 — Salida final legible.** El resumen final de install.sh (patrón install.sh:229-230) reporta también el timer y su binario: ruta del unit timer, ruta de `mofgw-sync`, y el comando de inspección (`systemctl --user list-timers mofgw-sync.timer`).

## Invariantes

- **I1 — El timer es el único scheduler; el service del sync jamás se auto-restartea.** `mofgw-sync.service` carece de `Restart=` y de cualquier política de reintentos (D3): un run fallido es visible (exit ≠ 0 → estado failed del oneshot) y el próximo vencimiento del timer lo re-intenta. Jamás `Restart=always/on-failure` en el service del sync (el patrón `Restart=on-failure` de install.sh:129 es EXCLUSIVO del server long-running).
- **I2 — El sync (bajo timer o manual) jamás escribe config.yaml fuera del contrato de 004.** I2 de 004 intacto; el timer solo cambia CUÁNDO corre el binario, no qué hace. Cero diffs en `internal/*` y `cmd/mofgw`.
- **I3 — El unit real del operador jamás se pisa sin backup.** Ningún path de 006 sobrescribe un unit existente con contenido distinto sin dejar `.bak.<ts>` byte-exacto antes (D6/P4). Los `.bak` son inmortales para install.sh.
- **I4 — install.sh no genera ni toca secrets.** P8: el env file es referencia read-only; las keys viven solo donde el operador las puso (precedente P13 de 005).
- **I5 — Superficie de cambios acotada.** NUEVOS: `scripts/systemd/mofgw-sync.service`, `scripts/systemd/mofgw-sync.timer`, `cmd/mofgw-sync/unitfiles_test.go`. MODIFICADOS: `scripts/install.sh`, `scripts/test-install.sh`. CERO cambios en: todo `internal/`, `cmd/mofgw/`, `cmd/mofgw-sync/main.go`, `config.example.yaml`, cualquier skill.
- **I6 — Fail-loud sobre silencio.** La instalación del sync falla con mensaje claro (die) si: el binario no pudo construirse/copiarse, la copia de units falla, o la verificación de agenda (D7) no confirma el timer activo. Jamás un install.sh exit 0 con timer ausente.
- **I7 — Una sola fuente de verdad de los units.** El contenido canonical vive SOLO en `scripts/systemd/`; install.sh COPIA (no re-genera heredocs para los units del sync); el golden test Go valida esa fuente única. Cero duplicación de contenido de units del sync.
