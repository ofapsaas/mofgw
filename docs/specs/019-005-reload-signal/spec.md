# 019-005 — Reload-signal: restart + verificación post-reload + rollback restore-only

## Descripción

- **D1 — Componentes (LOCKEADA, decisión HITL 5).** Dos piezas:
  1. Paquete puro **`internal/reloadsig`**: orquesta la fase de reload a partir de datos e interfaces inyectadas. Entradas: bytes previos del config (`stash []byte`, los leídos al inicio del run), path del config (`configPath`), reporte de 004 (`Applied bool`, `Skipped bool`, `Digest string`), unidad systemd (`unit string`), y las interfaces `SystemdCtl`, `Prober`, `FS`, `Logger`. Salida: exit code + eventos logueados. Imports permitidos: `internal/config` (solo `ParseForValidation` para derivar el set esperado), stdlib (`crypto/sha256`, `encoding/hex`, `encoding/json`, `fmt`, `net/url`, `sort`, `strings`, `time`). JAMÁS `configsync`, `catalogmerge`, `proxy`, `router`, `cmd/mofgw`, `modelscache`. Sin I/O, sin red, sin `os/exec` reales, sin log propio — todo inyectado (patrón D9/I1 de 004).
  2. Extensión del binario **`cmd/mofgw-sync/main.go`**: adapter fino que, tras la fase 004 exitosa, invoca `reloadsig.Run(...)` con las implementaciones reales (`osFS`, `exec.Command`-backed SystemdCtl, `net/http` Prober, slog). El binario sigue siendo el ÚNICO que toca disco y loguea (I1 de 004 se preserva; la excepción del rollback se delimita en I3).
- **D2 — Descubrimiento estructural que lockea la forma (LOCKEADA).** No existe NINGÚN mecanismo de reload de config en el servidor: config cargado una vez al boot (cmd/mofgw/main.go:72), único signal handling INT/TERM (main.go:369), cero SIGHUP en el repo, wiring providers/pricing/metadata 100% pre-tráfico (main.go:90-126, 244-258, 326). El epic 017 verificado (`017-mofgw-client-hot-reload`, plan.md:9,15) es hot-reload de **clients.yaml vía polling**, NO de providers[] y NO vía SIGHUP. Conclusión estructural: **restart es la única vía de aplicación hoy y lo seguirá siendo para providers[]/pricing/metadata incluso cuando 017 retome** — la alternativa "SIGHUP cuando 017 retome" del plan epic se descarta por incorrecta (mapeo, no temporalidad). En consecuencia 005 es **restart-only** y JAMÁS envía SIGHUP (I5).
- **D3 — Trigger de restart (LOCKEADA, decisión HITL 2).** Restart INCONDICIONAL cuando `Applied=true` y `--no-reload` ausente: pricing/metadata/models se construyen todos al boot (main.go:244-258), no hay distinción aplicable. `Skipped=true` → NO restart (solo defensa M-2, D8). Sin flag `--no-reload` → fase completa.
- **D4 — Mecanismo de restart (LOCKEADA).** `systemctl --user restart <unit>` con `unit` fijo `"mofgw.service"` (nombre del deploy real, verificado en `~/.config/systemd/user/mofgw.service`). Sin flag de override del nombre: la superficie de config mínima manda (006 poseerá unit/timer; si algún día el unit cambia de nombre, es cambio de 006, no knob de 005). El timeout del comando restart es 30s (espeja `TimeoutStartSec=30` del unit real).
- **D5 — Verificación en 3 fases ordenadas (LOCKEADA).** Tras restart exitoso: (F1) `systemctl --user is-active mofgw.service` == active, polleado cada 1s dentro de una ventana de 30s (patrón install.sh:165-168); (F2) `GET http://<server.addr>/healthz` con HTTP 2xx, polleado cada 1s, request timeout 2s, ventana 30s (patrón install.sh:173-179); (F3) `GET http://<server.addr>/v1/models` con paridad de IDs (D6). `server.addr` se deriva del ParseForValidation del config escrito (default `127.0.0.1:3369`, config.go:415); esquema HTTP fijo `http://` (el server no sirve TLS).
- **D6 — Paridad de IDs (LOCKEADA).** El set esperado = unión DEDUP de `providers[].models` del config escrito (ParseForValidation sobre los bytes en disco post-write — el binario NO retiene los bytes del candidato, los lee del disco ya validado por 004). Lo asertado contra `/v1/models`: HTTP 200 + `object == "list"` + set de `data[].id` == set esperado como SET (sorted dedup, orden irrelevante — el orden del catálogo no es la cadena de fallback). JAMÁS se compara el campo `created` (es `time.Now()` por entry, proxy.go:1222) ni el body completo.
- **D7 — Auth de verificación (LOCKEADA, decisión HITL 1).** Key de cliente dedicada vía env `MOFGW_SYNC_VERIFY_KEY` (key registrada en clients.yaml; el sync la usa como `Authorization: Bearer` en F3). Seteada → paridad automatizada obligatoria en F3. Unset → **degradación fail-soft**: F1+F2 únicamente + un warning logueado (`verify_key_unset`); exit code sigue 0 si F1/F2 pasan. La paridad automatizada queda documentada como requerimiento de la key (README/skill doc).
- **D8 — Defensa M-2 skip-trap (LOCKEADA, decisión HITL 4).** Si 004 reportó `Skipped=true`: 005 lee config.yaml en disco, computa sha256 hex y lo compara contra el `Digest` del reporte de 004 (= digest del candidato). Mismatch → **fail-loud exit 1, log descriptivo (`skip con config en disco ≠ candidato — sospecha skip-trap sidecar-primero`), SIN restart**. Match → exit 0 (skip legítimo, config en disco == candidato). NO se modifica 004 (D6 de 004 lockeada); esta defensa es 100% lado 005, read-only sobre el config.
- **D9 — Rollback restore-only (LOCKEADA, decisión HITL 3).** Cualquier fallo en D4-D6 (restart command error, F1 timeout, F2 fail, F3 fail/401) con `Applied=true`: (1) restaurar los bytes PREVIOS del config — los leídos al inicio del run, ANTES de que 004 escribiera — vía escritura atómica **RESTORE-ONLY**: temp en el mismo directorio + Chmod preservando el mode vigente + fsync + rename (patrón writeAtomic de configsync/apply.go:82-108 reimplementado localmente — unexported, reloadsig no importa configsync); (2) re-restart; (3) re-verificar F1+F2 SOLAMENTE (los bytes restaurados son la config previa conocida-válida — su paridad de catálogo no se re-aserta, solo liveness). Fundamento HITL: quedarse con el server caído en loop de `Restart=on-failure` es peor que volver a la config anterior válida.
- **D10 — Rollback agotado (LOCKEADA).** Si el restore, el re-restart o la re-verificación fallan → fail-loud **exit 3** con log descriptivo de la fase exacta que falló (el server puede quedar caído o con config previa pero sin verificar — estado expuesto en el log, nunca silenciado).
- **D11 — systemd no disponible (LOCKEADA).** Si `systemctl` no existe/no es ejecutable (host sin systemd user manager), chequeado ANTES de intentar restart: **fail-loud exit 3, sin rollback, sin restart**. Justificación: el config nuevo ya está escrito y es válido (004 garantizó); sin systemd ni se puede verificar ni se puede restaurar con garantía de consistencia (el server sigue corriendo con la config vieja en memoria — restaurar bytes no cambia lo que el server cargó y agregaría una divergencia disco-vs-memoria sin ninguna verificación posible). El operador decide manualmente; el log describe el estado exacto y la acción sugerida.
- **D12 — Escape operativo `--no-reload` (LOCKEADA, decisión HITL 5).** Flag nuevo del binario: aplica el config (fase 004 completa) pero NO restartea, NO verifica, NO rolea back. Casos de uso: streams en curso en producción, testing, y preparación del timer de 006. Exit code hereda la semántica 004 (0/1/2).

## Contrato (postcondiciones)

- **P1 — Trigger.** La fase de reload corre SOLO si: 004 terminó con exit 0 Y (`Applied == true` Y `--no-reload` ausente) O (`Skipped == true`, en cuyo caso corre únicamente la defensa M-2 de P2). `Skipped == true` JAMÁS dispara restart (D3). `--no-reload` presente → NINGUNA fase de reload/verificación/rollback corre (ni siquiera el chequeo M-2, que solo protege al path de reload); exit = exit de 004.
- **P2 — Defensa M-2.** Con `Skipped == true`: sha256 hex de los bytes de config.yaml en disco == `Digest` del reporte → exit 0 con log `skip verificado`. Mismatch → exit 1, log con ambos digests (disco vs reporte), restart JAMÁS ejecutado. El chequeo es read-only (jamás escribe config ni sidecar).
- **P3 — Restart.** Con `Applied == true` y sin `--no-reload`: el binario ejecuta exactamente `systemctl --user restart mofgw.service` (unit constante, D4) con timeout de comando 30s. Falla el comando → rollback de P7.
- **P4 — Fase F1 (is-active).** Tras restart: `systemctl --user is-active mofgw.service` debe reportar activo dentro de 30s (poll 1s). No activo al agotar la ventana → rollback de P7.
- **P5 — Fase F2 (healthz).** Tras F1 ok: `GET http://<server.addr>/healthz` (addr derivado del config escrito, D5) debe responder 2xx dentro de 30s (poll 1s, request timeout 2s). Sin 2xx al agotar → rollback de P7. `/healthz` es público (proxy.go:381) → sin auth, jamás se envía Bearer acá.
- **P6 — Fase F3 (paridad).** Tras F2 ok y con `MOFGW_SYNC_VERIFY_KEY` seteada: `GET http://<server.addr>/v1/models` con `Authorization: Bearer <key>`, request timeout 5s, un solo request (sin retry: la fase ya garantizó server listo). Falla HTTP (no-200, incluido 401) o JSON no-parseable o `object != "list"` o set de `data[].id` ≠ set esperado (D6) → rollback de P7. La comparación es por SET (sorted, dedup); el campo `created` y cualquier campo extra/ausente de metadata/pricing NO participan del veredicto.
- **P7 — Rollback restore-only.** Ante fallo de P3/P4/P5/P6: los bytes de config.yaml en disco pasan a ser EXACTAMENTE los bytes previos (stash leído al inicio del run), escritos vía temp-en-mismo-dir + Chmod (mode vigente, default 0600 si no existía) + fsync + rename. Los bytes restaurados son los leídos, jamás derivados/regenerados (D9). Falla la escritura del restore → salto directo a exit 3 (D10) con log del error de I/O.
- **P8 — Re-restart y re-verificación del rollback.** Tras restore exitoso: un (1) `systemctl --user restart mofgw.service` adicional (timeout 30s) + F1 (ventana 30s) + F2 (ventana 30s). Ambas pasan → exit 3 (fail-loud con rollback COMPLETO: el operador debe saber que se restauró; el exit no es 0 aunque el server esté vivo — la config nueva NO quedó aplicada). Cualquiera falla → exit 3 con la fase fallida en el log (D10). El veredicto del rollback JAMÁS es exit 0.
- **P9 — Degradación sin key.** Con `MOFGW_SYNC_VERIFY_KEY` unset y F1/F2 ok: NO se llama `/v1/models`, se loguea warning `verify_key` una vez, exit 0. Con key seteada y F3 recibiendo 401 → rollback de P7 (la key configurada inválida es un fallo de verificación, no una degradación).
- **P10 — systemd no disponible.** `systemctl` ausente/no ejecutable → exit 3, log descriptivo (estado: config nuevo escrito y válido, server sin verificar, restart no intentado), cero rollback, cero restart. La detección precede a P3.
- **P11 — Exit codes (extensión de P15 de 004).** **0** = config escrito OK + reload/verificación OK; O skipped byte-idéntico con digest verificado (P2); O skipped y `--no-reload`. **1** = fail-loud PRE-restart: config vigente inválido, Merge sin fuentes, validación del candidato falla, I/O de 004, YAML inválido, o defensa M-2 con mismatch. **2** = flags/uso inválido (incluye `--no-reload` malformado). **3** = `Applied == true` pero reload/verificación falló (rollback intentado — exitoso o agotado — y jamás exit 0). En 3 el config.yaml puede estar en estado NUEVO (systemd ausente) o PREVIO (rollback aplicado) — el log lo declara explícitamente en cada caso.
- **P12 — Logging estructurado por fase.** Cada fase emite un record slog con atributo `phase` ∈ {`m2_check`, `restart`, `is_active`, `healthz`, `parity`, `rollback_restore`, `rollback_restart`, `rollback_verify`, `degraded`} y campos suficientes para reconstruir el veredicto (unit, url, digests cuando aplique, error exacto). Info en éxito, Warn en degradación, Error en fallo. El orden de emisión refleja el orden de ejecución real.
- **P13 — Sin secrets.** `MOFGW_SYNC_VERIFY_KEY` y el header `Authorization` JAMÁS aparecen en logs (ni en claro ni truncados). Solo se loguea si la key estaba seteada/unset, nunca su valor.
- **P14 — Sidecar intocado por el rollback.** El restore de P7 reescribe SOLO config.yaml, jamás el sidecar `.sha256` (queda con el digest del candidato → el próximo run de 004 detectará mismatch y auto-curará reescribiendo el candidato, P10 de 004 — y la defensa M-2 de P2 impedirá re-aplicar una config que mató al server sin intervención del operador: fail-loud en cada corrida hasta que el root cause se corrija). `clients.yaml` jamás tocado por 005.
- **P15 — Precedencia y unit.** El `configPath` de la fase de reload es el MISMO resuelto por 004 (flag > home > /etc — main.go:141-168). El `stash` de rollback son los bytes de ESA lectura (P1 de 004: un solo read del raw por run). El `unit` es la constante `"mofgw.service"` (D4).

## Invariantes

- **I1 — Superficie de cambios.** Archivos NUEVOS: `internal/reloadsig/reloadsig.go`, `internal/reloadsig/reloadsig_test.go` (más los que el test-writer determine bajo ese paquete). Archivo MODIFICADO: `cmd/mofgw-sync/main.go` únicamente (extensión de `run` post-fase-004 + flag `--no-reload` + wiring de implementaciones reales). CERO cambios en: `internal/configsync`, `internal/catalogmerge`, `internal/modelsdev`, `internal/upstream`, `internal/modelscache`, `internal/config`, `internal/proxy`, `internal/router`, `cmd/mofgw` (código lockeado de 001-004 intacto; delimitación de I3 de 004 respetada).
- **I2 — Pureza de `internal/reloadsig`.** Sin `os/exec`, sin `net/http`, sin `os.*` concretos, sin log, sin reloj real: `SystemdCtl`, `Prober`, `FS` y `Logger` son interfaces inyectadas. El binario es el único punto de implementación real (`exec.Command`, `http.Client`, `osFS` ya existente, `slog`).
- **I3 — Excepción de escritura guardada (única en el epic).** El contrato I2 de 004 ("solo configsync escribe config.yaml") adquiere UNA excepción: el rollback RESTORE-ONLY de P7. Es segura porque: (a) escribe bytes LEÍDOS del config previo, jamás derivados (cero serialización, cero lógica de contenido en reloadsig); (b) usa el mismo patrón atómico temp+chmod+fsync+rename verificado en 004 (P9 de 004); (c) solo se dispara tras un fallo de verificación post-restart, nunca en el path feliz; (d) no toca el sidecar (P14) → auto-cura de 004 intacta. writeAtomic de configsync es unexported y reloadsig no importa configsync → reimplementación local (precedente exacto: D6 de 004 reimplementó writeFileAtomic de modelscache).
- **I4 — Servidor mofgw sin cambios.** Cero diffs en `cmd/mofgw` e `internal/{proxy,router,registry,auth,...}`: el server sigue siendo el mismo binario que carga config una vez (contrato epic plan.md:50). 005 no agrega endpoints, handlers, ni signal handling.
- **I5 — Jamás SIGHUP.** Ningún path de 005 envía señales distintas del restart systemd (D2). Si el server un día implementa hot-reload real, es una feature propia que re-evalúe esta decisión — no un knob de 005.
- **I6 — Sin secrets (transversal).** P13 aplica a TODOS los logs de la fase (incluidos errores HTTP: se loguea status code y URL, jamás headers).
- **I7 — Fail-loud sobre silencio.** Todo estado anómalo (M-2 mismatch, systemd ausente, rollback, degradación) es VISIBLE: exit code ≠ 0 o log de nivel ≥ Warn con fase explícita. 005 jamás reporta éxito sin haber verificado lo que declara verificar.

## Fuera de alcance

- **Hot-reload de providers/config in-server (SIGHUP, polling, endpoint admin):** estructuralmente fuera hasta decisión futura — el descubrimiento verificó que ni hoy ni con 017 retomada existirá (017 es clients-polling). Cualquier hot-reload real es feature propia con HITL.
- **Cambios al servidor mofgw** (cmd/mofgw, proxy, auth, router): jamás (epic plan.md:50).
- **Unit file systemd y timer (019-006):** 005 asume el deploy existente; no instala, no edita, no crea units ni timers ni knobs de scheduling.
- **Rollback del sidecar `.sha256`:** el rollback toca solo config.yaml; el sidecar se auto-cura vía 004 (P14).
- **Modificaciones a 001-004** (fetch, upstream, catalogmerge, configsync, ParseForValidation): cero.
- **Verificación de paridad de pricing/metadata en el body de /v1/models:** solo IDs son veredicto (la metadata ya fue validada por 004 pre-write; el enriquecimiento server-side está congelado por tests existentes).
- **Curl sin auth documentado en el skill mofgw-client-sync (stale, R3):** corregir la doc del skill es trabajo del merge de documentación, no código de esta feature.
